# 数据：能力的主要来源

代码决定模型“能怎样学习”，数据决定它“实际学到什么”。附带 demo 只有几十条，用途是捕获管线错误，不是构建通用助手。

## 预训练

格式：UTF-8 纯文本，每个非空行视为一个独立文档。

```text
第一段完整文本。
第二段完整文本，可以更长。
```

准备阶段会为每行加入 `<bos>/<eos>`，编码为 little-endian `uint32` 连续 token 文件。训练 Dataset 使用 memmap，把连续流切成固定 `max_seq_len+1` 窗口；窗口之间没有 padding 浪费。

建议在正式训练前至少完成：

1. 确认许可证允许训练与发布；
2. 去除密码、令牌、个人隐私和不需要的 HTML 噪声；
3. 基于内容哈希去重，而不只是文件名去重；
4. 划分 train/eval 后再训练，避免同一文档跨集合；
5. 统计字符、语言、长度、重复率和 token 数。

## SFT

每行一个 JSON 对象，顶层必须有 `messages`：

```json
{"messages":[
  {"role":"system","content":"你是一个可靠的中文助手。"},
  {"role":"user","content":"什么是梯度累积？"},
  {"role":"assistant","content":"多个小批次先累加梯度，再统一更新一次参数。"}
]}
```

支持 `system/user/assistant` 三种 role。实现只让 assistant 的正文、`<|end|>` 和最终 `<eos>` 产生 loss；system、user 与角色 token 只是条件。这避免模型被训练成“续写用户问题”。

多轮对话可以继续追加 user/assistant。超长样本会在 `max_seq_len` 处截断，因此数据清洗时最好主动控制长度，并检查截断后是否还保留 assistant 监督 token。

## DPO

```json
{"prompt":[
  {"role":"system","content":"你是一个诚实的助手。"},
  {"role":"user","content":"你永远正确吗？"}
],"chosen":"不会，我有能力边界。","rejected":"会，我永远正确。"}
```

`chosen` 与 `rejected` 必须针对完全相同的 prompt，差异应集中在你希望优化的行为。若 rejected 只是更短、更长或格式明显不同，模型可能学到表面捷径。

DPO 不是知识注入的替代品。模型若从未学过某个领域，仅靠偏好标签不能凭空获得可靠事实。

## 多少数据才够

不存在只看参数量就能给出的固定答案。可以遵循逐级验证：

- demo：几十条，只检查代码；
- 窄领域原型：数百万到数千万高质量 token；
- 更通用的小模型：通常需要数亿乃至更多有效 token；
- SFT：质量与覆盖面常比单纯条数更关键；
- DPO：先做小规模人工审计，确认偏好方向没有系统性错误。

每次扩大前保留一组固定评测提示和失败样例。没有测量，就无法知道“更大”是否真的“更智能”。
